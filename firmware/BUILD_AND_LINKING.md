# PUSHPAK firmware — build & script linking

How the **compiled firmware** (native AP_IDS in C++) and the **Lua confirmation scripts**
fit together, and how to link the scripts to a build — either by copying to the SD card
(no rebuild) or by baking them into the firmware image (rebuild).

All builds are **ArduCopter V4.7.1, git `dbe79216` plus local AP_IDS patches, board Pixhawk6C**.
`../configs/capabilities.json` holds the machine-checked facts. It is generated by
`scripts/discover_firmware.py` and currently describes **build_v3**.

### Build history

| Build | APJ SHA-256 | `ids` binding | Native detectors driven | `AP_IDSGCS::report_confirmed` | ROMFS scripts embedded |
|---|---|---|---|---|---|
| 26 Sep 2026 (`shareable_progress/build.zip`) | — | 2 methods | GPS, IMU, Mission | stub (returns false) | the original scripts (fail at `dofile`) |
| **build_v3**, 4 Oct 2026 (technical reference) | `223c26f8…` | 26 methods (adds `<det>_confidence/_evidence/_state`) | all 8 | implemented | older copies of 6 of the current scripts (DISC-005) |
| 14 Oct 2026 patch build (`pushpak_ap_ids_Copter-4.7.1.patch`) | `3fab3632…` | 3 methods (adds `get_channel`) | all 8 (SITL log) | implemented | not analysed |

The build_v3 facts were checked against its ELF on 9 Nov 2026. The 14 Oct facts come from its patch file and SITL log only; no ELF was available. Which build is the release is not decided yet (FW-00 in `FIRMWARE_WORK_REQUIRED.md`).

## 1. The two firmware pieces and how they link

```
        ┌──────────────────────────── FLIGHT CONTROLLER (Pixhawk 6C) ────────────────────────────┐
        │                                                                                          │
        │   libraries/AP_IDS/  (native C++, first stage)          AP_Scripting  (Lua, second stage)│
        │   ┌───────────────────────────┐                         ┌──────────────────────────────┐│
        │   │ AP_IDS.cpp   AP_IDSGCS.cpp │      Lua binding        │ scripts/*_confirm.lua         ││
        │   │ GPSDetector  IMUDetector   │◄──────────────────────►│ scripts/modules/ids_common.lua││
        │   │ MAVLinkDetector Mission…   │  ids:report_confirmed()│                                ││
        │   │ Command/Param/RC/Offboard  │  ids:event_sequence()  │ standard bindings:            ││
        │   └─────────────┬──────────────┘                         │  gps: ahrs: ins: rc: vehicle:││
        │                 │ AP_IDSGCS (STATUSTEXT)                  │  arming: mission: param: gcs:││
        │                 ▼                                         └───────────────┬──────────────┘│
        │           MAVLink STATUSTEXT  ◄──────── gcs:send_text()  (PIDS / PUSHPAK IDS lines) ──────┘
        └─────────────────┬────────────────────────────────────────────────────────────────────────┘
                          │  telemetry link (UDP/TCP/serial)
                          ▼
                   SPIDERS.Mk1 GCS  (parses PIDS|… and PUSHPAK IDS: … lines)
```

**The link between the two is the `ids` Lua binding.** ArduPilot's scripting generator
turns a *binding descriptor* into C++ glue (`libraries/AP_Scripting/lua_generated_bindings.cpp`)
so Lua can call into the `AP_IDS` singleton. Every build has these two methods
(confirmed from the ELF symbol tables):

| Lua call | C++ target | Purpose |
|---|---|---|
| `ids:report_confirmed(name,state,conf,evidence,metric,instance,seq)` | `AP_IDS::report_confirmed(...)` | Lua pushes a confirmed result back into native AP_IDS |
| `ids:event_sequence()` | `AP_IDS::event_sequence()` | native event counter Lua can read |

build_v3 also has per-detector accessors (`ids:gps_confidence()`, `ids:gps_state()`, …),
and the 14 Oct build has `ids:get_channel()`. The 26 Sep build has neither. The scripts here
use only the two methods above, so they run on every build. They derive their own evidence
from the standard `gps:`/`ahrs:`/`ins:`/… bindings. See `README.md` in this folder for the
per-script detail.

## 2. What's in a build artifact (example: the 26 Sep `shareable_progress/build.zip`)

This section describes the **26 Sep 2026 build**. build_v3 has the same layout; its
differences are in the build history table above.

A build zip is a **compiled artifact**, not a source tree — you can flash it, but you can't
`waf`-build from it alone.

```
build/Pixhawk6C/
├── bin/arducopter.apj          ← flashable image (Mission Planner / QGC / uploader)
├── bin/arducopter.bin          ← raw binary
├── bin/arducopter              ← ELF (used for source-of-truth discovery)
├── ap_romfs_embedded.h         ← the scripts CURRENTLY baked into ROMFS (the OLD, broken ones)
└── libraries/AP_IDS/*.o        ← compiled native detectors:
        AP_IDS  AP_IDSGCS  GPSDetector  IMUDetector  MAVLinkDetector
        MissionDetector  CommandDetector  ParameterDetector  RCDetector  OffboardDetector
```

Two facts that decide how you link the scripts:

* **Older scripts are embedded in the image's ROMFS** (`ap_romfs_embedded.h`). On the 26 Sep
  build they are the original, broken scripts. On build_v3 they are older copies of 6 of the
  current scripts (DISC-005). If you drop new scripts on the SD card without disabling ROMFS
  scripts, the firmware runs **both**.
* **`AP_IDSGCS::report_confirmed`** was a stub returning `false` on the 26 Sep build
  (DISC-002). build_v3 and the 14 Oct build implement it. The scripts' own `gcs:send_text()`
  STATUSTEXT lines reach the GCS on every build.

## 3. Scripts in this folder

```
firmware/
├── scripts/
│   ├── gps_confirm.lua        mavlink_confirm.lua    command_confirm.lua
│   ├── jamming_confirm.lua    imu_confirm.lua        mission_confirm.lua
│   ├── parameter_confirm.lua  offboard_confirm.lua   ids_gcs_bridge.lua
│   └── modules/
│       └── ids_common.lua     ← shared helpers + hysteresis state machine (require()d)
└── ROMFS_custom_fixed.zip     ← the same tree, zipped, ready to drop into ROMFS
```

`ids_common.lua` **must** live in `scripts/modules/` (not next to the scripts). ArduPilot
runs every `.lua` in `scripts/` as a standalone script, and its `package.path` for
`require()` is `@ROMFS/scripts/modules/?.lua;…;/APM/scripts/modules/?.lua`. Each script
loads it with `require("ids_common")` (this firmware has no `dofile`).

## 4. Link path A — SD card (no rebuild, recommended for testing)

Fastest way to run the fixed scripts on the existing firmware.

1. Power off, remove the microSD card, and copy the tree so the card contains:

   ```
   APM/scripts/
       gps_confirm.lua  mavlink_confirm.lua  command_confirm.lua  jamming_confirm.lua
       imu_confirm.lua  mission_confirm.lua  parameter_confirm.lua  offboard_confirm.lua
       ids_gcs_bridge.lua
       modules/
           ids_common.lua
   ```

2. Set parameters (Mission Planner / QGroundControl → Config → Full Parameter List):

   | Parameter | Value | Why |
   |---|---|---|
   | `SCR_ENABLE` | `1` | enable Lua scripting |
   | `SCR_DIR_DISABLE` | `1` | **skip the OLD scripts baked into ROMFS** (critical — see §2) |
   | `SCR_HEAP_SIZE` | raise if you see `not enough mem, increase SCR_HEAP_SIZE` | 9 scripts need more than the default heap |

3. Reboot the flight controller.

4. Verify (GCS messages tab): you should see
   `PUSHPAK IDS: BRIDGE binding=report_confirmed,event_sequence v=2`, a `STATEMAP` line,
   `SYNC` lines every 10 s, and **no** `Lua: … error` lines. In SPIDERS.Mk1, the IDS page
   shows the scripts as RUNNING under Lua script health, and the FC EVENT DELIVERY strip
   shows bridge v2.

No firmware rebuild is needed; ArduPilot loads SD-card scripts at boot.

## 5. Link path B — bake into the firmware (ROMFS, needs a rebuild)

Use this when you want the current scripts inside the flashed image (no SD dependency, and
it clears DISC-005), or for the native work items in `FIRMWARE_WORK_REQUIRED.md`. On the
26 Sep build it was also the way to fix the native side (the `AP_IDSGCS` stub and the
un-wired detectors); build_v3 already has those fixes.

You need the **ArduPilot source tree at the exact commit** `dbe79216` with the AP_IDS
patches (a build zip is a compiled artifact and can't be built from):

```bash
git clone https://github.com/ArduPilot/ardupilot
cd ardupilot && git checkout dbe79216
git submodule update --init --recursive
```

1. **Place the AP_IDS library and scripts** in the tree:
   * `libraries/AP_IDS/` — the native detector sources. The current tree (engine included) is
     in `GNSSIntegrity_snapshot/ardupilot_untracked_AP_IDS_and_ROMFS.tar.gz`; apply
     `GNSSIntegrity_snapshot/ardupilot_tracked_changes.patch` on `dbe79216` for the Copter,
     binding and waf changes.
   * `ROMFS_custom/scripts/` **at the tree root** — copy this folder's `scripts/` **including
     `modules/`** (or unzip `ROMFS_custom_fixed.zip` at the root). `Tools/ardupilotwaf/boards.py`
     embeds every file under `ROMFS_custom/`; no other location is picked up.
2. **Link the Lua binding** (from the project's integration artifacts, per `VALIDATION.md`):
   ```
   git apply ArduCopter_IDS_integration.patch      # registers AP_IDS + hooks AP_IDS::update()
   cat AP_IDS_bindings.desc.append >> libraries/AP_Scripting/generator/description/bindings.desc
   ```
   The appended lines declare the `ids` singleton and its methods; `waf` regenerates
   `lua_generated_bindings.cpp`. To also expose the per-detector accessors, add them here.
3. **Build** (SITL first to validate, then the board):
   ```bash
   ./waf configure --board sitl && ./waf copter        # test in SITL
   ./waf configure --board Pixhawk6C && ./waf copter    # → build/Pixhawk6C/bin/arducopter.apj
   ```
   On the **board** build, `ap_romfs_embedded.h` is regenerated with the **new** scripts,
   so you don't need `SCR_DIR_DISABLE`. Still set `SCR_ENABLE=1`, and raise `SCR_HEAP_SIZE`
   (the nine scripts plus any other script exhaust the default 200 KB heap).

   **SITL builds do not embed `ROMFS_custom/scripts/`.** The local patch to `SITLBoard` in
   `Tools/ardupilotwaf/boards.py` drops them, because with the scripts in ROMFS every upstream
   scripting autotest ran out of heap (`not enough mem, increase SCR_HEAP_SIZE`) and failed
   with "Prearm bit never went true". Test the scripts on SITL through `scripts/` (§6).
4. **Flash** `build/Pixhawk6C/bin/arducopter.apj` and reboot.

Recommended production sequence (from `VALIDATION.md`): apply patch → append binding desc →
`./waf distclean` → build SITL → install scripts → wire remaining native adapters → replay
benign+attack traces and tune thresholds → build for Pixhawk6C and check flash/RAM deltas →
HIL/bench test before flight.

## 6. Verify the link (SITL, no hardware)

SITL loads scripts from `scripts/` in its working directory (path A; ROMFS scripts are not
embedded in SITL builds, see §5):

```bash
mkdir -p scripts && cp -r <SPIDERS>/firmware/scripts/. scripts/     # in the SITL working dir
Tools/autotest/sim_vehicle.py -v ArduCopter --out=udp:127.0.0.1:14550
# in MAVProxy:  param set SCR_ENABLE 1 ; param set SCR_HEAP_SIZE 400000 ; reboot
# then connect the GCS:  SPIDERS.Mk1 → Connection → udp:127.0.0.1:14550
```

Checked on 4.7.1 SITL (11 Nov 2026, engine compiled in): no `Lua:` errors; the bridge sends
`BRIDGE binding=report_confirmed,event_sequence v=2`, `STATEMAP` and `SYNC`; three
`ATC_ANGLE_MAX` changes while armed go SUSPECTED → CONFIRMED and native AP_IDS prints
`[PIDS] PAR THREAT LV1` then `LV2`; the GNSS engine writes `IDSG` (1 Hz, state 4 VALID when
stationary) and five `IDSR` rows per `IDSG`. Known noise: the bridge sends `FC_EVENT` about
once a second on an idle vehicle, because a native detector (not the GNSS engine) toggles its
state or evidence about twice a second.

Offline, run the script test harness (Lua 5.4 with firmware-accurate binding mocks):

```bash
cd ../backend && PYTHONPATH=. ../.venv/bin/python -m pytest -q tests/test_lua_scripts.py
```

It checks that each fixed script stays quiet on benign data and confirms its attack, and that
the GCS parses their output. The check that the original scripts fail on the 26 Sep binding
runs only when the original `ROMFS_custom.zip` is present. The tests need the `lupa` package.

| File / dir | Role |
|---|---|
| `scripts/*_confirm.lua` | eight per-detector Lua confirmation scripts (second stage) |
| `scripts/ids_gcs_bridge.lua` | bridge protocol v2: announces binding/state map, SYNC, reports native `event_sequence()` changes |

| `GNSSIntegrity_snapshot/` | the ArduPilot working tree: base commit, tracked-file patch, `libraries/AP_IDS` + `ROMFS_custom` tarball, last SITL build log. Base + patch + tarball reproduces the tree exactly |
| `native/` | portable GNSS integrity engine, its host tests, and the reference adapter (opt-in defaults) |
| `README.md` | what each script detects and why (the fix detail) |
| `../configs/capabilities.json` | machine-checked firmware facts + discrepancies |
| `shareable_progress/build.zip` | the 26 Sep 2026 compiled firmware artifact (flashable, not buildable) |
| `FIRMWARE_WORK_REQUIRED.md` | firmware changes still needed (release baseline, DataFlash records, hooks, trust) |
