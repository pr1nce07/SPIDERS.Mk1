# SPIDERS.Mk1
**Security Packet Intrusion Detection Evaluation and Response System**, the ground control, IDS and forensics platform for the PUSHPAK UAV IDS.

A ground control station and IDS for Pixhawk 6C running ArduPilot with the PUSHPAK IDS firmware. It combines a live GCS view, distributed intrusion detection, incident correlation, forensic evidence cases, a visual IDS rule builder and flight replay. It was built from `PUSHPAK_GCS_IDS_BUILDER_MASTER_PROMPT.md`.

**The GCS is read-only.** It only receives MAVLink. No transport or API can send commands to a vehicle. Detection does four things: it detects, records, alerts and preserves evidence.

## Run

### Windows (PowerShell)

One-time setup (Python 3.11+ and Node.js required):

```powershell
py -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Push-Location frontend
npm install
Pop-Location
```

Build the frontend and start the app at http://127.0.0.1:8600:

```powershell
.\scripts\start.ps1
```

For frontend development with hot reload, run the backend and Vite in separate terminals:

```powershell
# Terminal 1
Push-Location backend
& ..\.venv\Scripts\python.exe run.py

# Terminal 2
Push-Location frontend
npm run dev  # open the URL printed by Vite
```

### macOS / Linux

```bash
# One-time setup
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
npm --prefix frontend install

# Build the UI, then start the app at http://127.0.0.1:8600
bash scripts/start.sh
```

For Vite development with hot reload, run the backend and `npm --prefix frontend run dev` in separate terminals. The dev server proxies `/api` and `/ws` to port 8600.

```bash
# tests (the Lua-script tests need the `lupa` package; without it they are skipped)
cd backend && PYTHONPATH=. ../.venv/bin/python -m pytest -q

# re-run source-of-truth discovery against a firmware build (zip of the waf build/ directory)
.venv/bin/python scripts/discover_firmware.py --build-zip <build.zip> --romfs-zip firmware/ROMFS_custom_fixed.zip \
    --ap-ids-source <ardupilot>/libraries/AP_IDS
```

To connect, use **Connection** in the top bar. Connection strings look like `udp:127.0.0.1:14550`, `tcp:127.0.0.1:5760`, `/dev/ttyUSB0:115200` or `COM3`. Simulation and Replay are also available there. Simulation runs 14 synthetic scenarios. These are real MAVLink frames generated in-process, and they are clearly labelled SIMULATION.

## Source-of-truth findings (`configs/capabilities.json`)
`configs/capabilities.json` is generated by `scripts/discover_firmware.py` from a real firmware build: the ELF symbol table and its disassembly, `ap_romfs_embedded.h`, and the `AP_IDS` source for the state enum. The current file describes **build_v3**, the build documented in the technical reference (APJ SHA-256 `223c26f8…`, built 4 Oct 2026, regenerated 9 Nov 2026).

| Item | Value (build_v3) |
|---|---|
| Firmware | ArduCopter V4.7.1, git `dbe79216` plus local AP_IDS patches, Pixhawk6C |
| AP_IDS detectors | All 8 families are driven: GPS, IMU and Mission from `AP_IDS::update()`; RC link and Parameter from `update_rc_link()` / `update_parameters()`; Offboard from `Copter::update_ids_offboard()`; MAVLink and Command from `GCS_MAVLINK_Copter::packetReceived()` |
| Lua `ids` binding | 26 methods: `report_confirmed()`, `event_sequence()` and `<det>_confidence/_evidence/_state()` for all 8 detectors |
| `AP_IDSGCS::report_confirmed` | Implemented (372 bytes of code; it is only a stub in builds without `HAL_GCS_ENABLED`) |
| PIDS state enum | Verified: `AP_IDS.h` has `static_assert`s for CLEAR=0, SUSPECTED=1, CONFIRMED=2 |
| Event ring | 8 slots, RAM only |
| Custom MAVLink / DataFlash IDS messages | None. The stock `ardupilotmega` dialect is used; native IDS DataFlash records are firmware work item FW-03 |

**Open discrepancy (shown under Settings → Firmware discovery):**
* **DISC-005**: build_v3 embeds older copies of `command_confirm.lua`, `ids_gcs_bridge.lua`, `jamming_confirm.lua`, `mavlink_confirm.lua`, `offboard_confirm.lua` and `modules/ids_common.lua` (comment-only difference) than `firmware/scripts/`. Either put the current scripts on the SD card and set `SCR_DIR_DISABLE=1` so ROMFS scripts are skipped, or rebuild the firmware with `firmware/ROMFS_custom_fixed.zip` (`firmware/BUILD_AND_LINKING.md` §4–5).

**Resolved.** These applied only to the earlier 26 Sep 2026 build (2-method binding) and are fixed in build_v3:
* DISC-001: the original scripts called accessor methods the binding lacked. build_v3 has the accessors, and the current scripts no longer need them.
* DISC-002: `AP_IDSGCS::report_confirmed` was a stub returning false.
* DISC-003: only GPS, IMU and Mission were driven.
* DISC-004: the PIDS state mapping was unverified.

A third build also exists, a 14 Oct 2026 patch build (APJ `3fab3632…`). It drives all 8 detectors and implements `report_confirmed`, but its binding has 3 methods (`report_confirmed`, `event_sequence`, `get_channel`). Which build is the release is not fixed yet: see FW-00 in `firmware/FIRMWARE_WORK_REQUIRED.md` and the build history in `firmware/BUILD_AND_LINKING.md`.

The gps_confirm.lua report is 81 characters, which is longer than a single 50-character STATUSTEXT. It therefore arrives chunked, and the GCS reassembles it using `id`/`chunk_seq`.

## Lua scripts
`firmware/scripts/` (packaged as `firmware/ROMFS_custom_fixed.zip`) is the current version of the PUSHPAK Lua scripts. They call only `ids:report_confirmed()` and `ids:event_sequence()`, so they run on every PUSHPAK build. See `firmware/README.md`. They are verified under Lua 5.4 against strict binding mocks by `backend/tests/test_lua_scripts.py`. The GCS parses their `PIDS|1|LUA|…` output and the bridge's `BRIDGE`, `STATEMAP`, `SYNC` and `FC_EVENT` lines (bridge protocol v2).

## Architecture
```
Source (UDP/TCP/Serial | .tlog | DataFlash | JSONL/CSV | case | simulation)
  → Decoder (raw bytes always preserved; BAD_DATA keeps bytes, error, recovered SYSID/COMPID)
  → TelemetryEvent → raw .tlog capture + SQLite (batched) + rolling buffer
  → VehicleState (AVAILABLE / STALE / UNAVAILABLE / INVALID, never a fake 0)
  → 18 detectors (each isolated in its own fault boundary) + published IDS-Builder rules
  → Correlator (explainable contributors; CONFIRMED needs ≥2 independent evidence lines: results that share a sensor/data path count once)
  → Incidents → automatic forensic case (30 s before + incident + 60 s after, SHA-256 sealed)
  → Event bus → WebSockets /ws/{telemetry,ids,incidents,events,health,builder} → React GUI
```
Live, replay and offline import all run through the same `Pipeline` class (`backend/app/core/pipeline.py`).

**Detectors:**
* HEARTBEAT, MAVLINK_SEQUENCE, SOURCE_IDENTITY, MAVLINK_RATE, MAVLINK_SIGNING
* GPS_INTEGRITY: rules, MAD robust z-score, EWMA, CUSUM, jump detection, GPS↔EKF residuals, EKF innovations, quality mismatch, persistence
* COMMAND, PARAMETER, MISSION (SHA-256 fingerprint), RC_LINK, IMU_CONSISTENCY, OFFBOARD
* BATTERY, FLIGHT_MODE, SENSOR_HEALTH
* PUSHPAK_FC (PIDS, Lua confirmations, Lua errors, bridge delivery tracking)
* BASELINE (signed, engineer-approved parameter/mission baseline; reports `BASELINE_MISMATCH`)
* ML_BASELINE (Isolation Forest, from an approved profile or an untrusted session baseline). This is supplementary only and never opens an incident on its own.

**Custom Ruleset:**
* Has 57 node types across five categories: input (16), transform (19), logic (10), correlation (6) and output (6).
* Rules are validated against the MAVLink registry. Validation catches unknown messages and fields, wrong types, bad operators, NaN or negative values, cycles and oversized graphs.
* You can test rules against synthetic scenarios, recorded captures, cases or imported logs, and check expected-trigger tests.
* It also has a live shadow debugger, a rule trace ("OPEN RULE TRACE"), immutable versions with SHA-256, publish/disable/clone, and undo/redo.
* Four built-in rules ship with it, including the §14 GPS/EKF example. All their expectation tests pass.

**Case directory:** `manifest.json`, `incident.json`, `timeline.jsonl`, `mavlink_raw.bin`, `mavlink_decoded.jsonl`, `telemetry.jsonl`, `ids_events.jsonl`, `gps_track.csv`, `attitude.csv`, `battery.csv`, `commands.jsonl`, `parameters.jsonl`, `rules/`, `screenshots/`, `hashes.sha256`, `case.sig.json` and `README.txt`.
* `mavlink_raw.bin` uses tlog framing. It is not a PCAP.
* `hashes.sha256` is compatible with `sha256sum -c`. Cases sealed on Windows before 9 Nov 2026 have `\r\n` lines in this file, so check those with VERIFY CASE instead.
* `case.sig.json` is an Ed25519 signature over the hash list. Cases sealed before evidence signing existed report UNSIGNED.
* VERIFY CASE returns VALID, MODIFIED, MISSING or UNVERIFIABLE, plus the signature status.
* Screenshots and custody events can be added only to a case that is still VALID. Each addition is recorded as a signed manifest revision and in the audit log.

**Other:**
* Audit log: append-only and hash-chained, with a verify endpoint. Signed checkpoints of the chain head can be mirrored to a separate store.
* Settings → Security: MAVLink signing keyring (secrets never leave the backend), evidence/approval public keys, audit checkpoints, approved baseline.
* Local mode: loopback only.
* Remote mode: bearer tokens stored as SHA-256 hashes, roles (operator < investigator < engineer < admin), and TLS is required.

## Known limitations
* **Not tested against real hardware.** No real Pixhawk, and no real .tlog or DataFlash file, was available. The UDP/TCP/serial transports and the DataFlash mapper are implemented but have only been exercised with simulated and synthetic data.
* **Latency shows N/A.** Measuring it needs TIMESYNC, which requires transmitting.
* **Signing can't be validated without the key.** Without an active keyring key (Settings → Security) or `signing_key_file`, signed frames show as SIGNED (unverified).
* **No reverse playback.** Detector state depends on order, so seeking backwards re-analyses from the start of the recording instead.
* **Detectors are synchronous.** The `process()` interface is synchronous (called in order) rather than `async`, which keeps the offline and live paths identical.
* **Screenshots need an open GUI.** They are captured by a connected GUI client (html2canvas), not by the backend.
* **Tailwind is not used.** The frontend uses its own CSS design system instead.
* **Thresholds are not tuned against real flights.** Detector thresholds in `configs/default.yaml` are initial values and should be tuned against real SITL and flight traces.

## SILKTRACE — universal drone evidence intake

The SILKTRACE module adds evidence-first intake for known and unknown drone blackbox formats. It stores immutable-by-policy originals, records SHA-256 hashes, performs progressive format inspection, and exposes a dedicated investigator workspace. It is an incremental extension: see [`docs/silktrace/README.md`](docs/silktrace/README.md) for supported formats, API routes, limitations and tests. Unknown-format acceptance is supported; universal semantic decoding is not claimed.

### SILKTRACE advanced analysis

SILKTRACE now includes GPS track replay, attitude-based 3D perspective replay, synchronized sample controls, DJI FlightRecord parsing (via `pydjirecord`), resource-limited isolated parser execution, firmware/log-format knowledge references, custom vehicle profiles, and robust statistical/IsolationForest anomaly screening. See [`docs/silktrace/ADVANCED_CAPABILITIES.md`](docs/silktrace/ADVANCED_CAPABILITIES.md) for limitations and deployment hardening. DJI v13–14 frame decryption requires per-flight DJI keychains; SILKTRACE does not fetch or store keys implicitly.
